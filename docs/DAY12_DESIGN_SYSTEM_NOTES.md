# Day 12 — reusable layout, navigation, typography, colour tokens and breakpoints

This is the Day 12 deliverable from `TODO.md`: "Establish reusable layout, navigation, typography, colour tokens and responsive breakpoints" (issue [#7](https://github.com/EdVialv/muizasmanor26/issues/7), which collectively covers the public directory/detail pages built across Days 12-15). Day 12 itself builds the shared shell every later page will sit inside - it does not build the directory, map or detail pages themselves.

## What this delivers

- `src/app/globals.css`: a documented token system (colour, typography scale, spacing scale, radius, a shared `.container` width, and a named breakpoint scale) replacing the one-off hardcoded values the Day 1 landing page shipped with.
- `src/components/SiteHeader.tsx`, `SiteFooter.tsx`, `AppShell.tsx`: a reusable header/footer and the shell that composes them around a page's own content.
- `src/app/layout.tsx` now renders every page inside `AppShell`, so every future page automatically gets the header, a single `<main>` landmark and the footer without having to build its own.
- `src/app/page.tsx` updated to drop its own `<main>` wrapper (now provided once, by the shell) and to use the new `.container` utility instead of a duplicated width rule.
- 8 new unit tests across three new test files (`SiteHeader.test.tsx`, `SiteFooter.test.tsx`, `AppShell.test.tsx`).

## Decisions made while writing this (flagged for Codex review)

1. **The colour palette and font stacks are unchanged from the Day 1 landing page - this pass tokenises and documents them, it does not redesign them.** `--ink`, `--muted`, `--paper`, `--surface`, `--accent`, `--line`, the serif heading font and the system-ui UI font are the exact same values, just promoted to a named, documented token set in `globals.css` instead of being scattered through the stylesheet. One new token was added: `--ink-contrast` (`#fff`), replacing a bare `color: white` that had no name before.
2. **Navigation shows only Home for now, by explicit owner decision.** The public site will eventually link to a directory, a map, an admin area and an enquiry form (Days 13-26), but none of those pages exist yet. Linking to them now would mean dead links; building throwaway stub pages for them now would mean redoing that work once the real page ships. The owner chose the third option directly: `SiteHeader`'s nav is a single `<ul>`/`<li>` with one Home link, structured so each later Day can append its own `<li>` to the same list without restructuring anything. `aria-current="page"` is hardcoded on that link for the same reason - Home is the only route that exists. **Once a second nav item is added, this needs to change to a client component using `usePathname()` from `next/navigation`** so the current item reflects the actual route instead of being assumed; this is noted directly in `SiteHeader.tsx`'s own comment so whoever adds the next nav item sees it.
3. **The header/footer/main composition lives in a separate `AppShell` component, not inline in `layout.tsx`.** Next.js's root `layout.tsx` has to return `<html>`/`<body>`, and a component that does that cannot be mounted the normal way with `@testing-library/react` (`render()` appends into an existing `document.body` that jsdom already owns - it doesn't let a component replace `<html>`/`<body>` itself). Pulling the header+main+footer composition into its own `AppShell` component, with `layout.tsx` just wrapping it in `<html>`/`<body>`, means the actual composition (skip link -> header -> main -> footer, exactly one `<main>`) is unit-tested directly, while `layout.tsx` itself stays limited to what it can usefully be tested for (the `metadata` export), matching the existing `layout.test.tsx` pattern from Day 1.
4. **Every page gets exactly one `<main>` landmark, owned by `AppShell`, not by each page.** `src/app/page.tsx` previously wrapped its own content in `<main>`; that's removed now that `AppShell` provides it once. A page that rendered its own `<main>` again would produce two `<main>` landmarks per document, which is invalid and breaks screen-reader "jump to main content" navigation. This is covered by a regression test (`AppShell.test.tsx`: "renders exactly one main landmark").
5. **A skip link is the first focusable element on every page.** `Pāriet uz galveno saturu` ("Skip to main content"), visually hidden until it receives keyboard focus, targeting `#main-content` on the `<main>` element `AppShell` renders. This did not exist before Day 12; it is a standard accessibility requirement for any site with a persistent header/nav, and was straightforward to add once a shared shell existed to put it in.
6. **The Day 1 `.featureSection` divider is now full-bleed (it spans the full viewport width, with an inner `.container` div holding the content), where it was previously width-constrained like the hero.** This is a deliberate, visible change, not an oversight: it matches how the new header/footer borders work (full-bleed line, constrained content inside), so every horizontal divider on the page now behaves the same way. The hero section itself is unchanged - it still carries the `.container` class directly, same as before.
7. **Breakpoints are documented as a comment, not stored as a custom property.** CSS custom properties cannot be used inside an `@media` condition - the browser needs a literal value at parse time. The scale (`--bp-sm: 40rem` / 640px, `--bp-md: 48rem` / 768px, `--bp-lg: 64rem` / 1024px) is written as a comment at the top of `globals.css` and the same literal rem values must be used in every `@media` rule, so later Days extending the stylesheet stay on the same scale instead of inventing new ad-hoc breakpoints. Only `--bp-sm` (40rem) is actually used yet, reusing the single breakpoint the Day 1 landing page already had; `--bp-md`/`--bp-lg` are reserved for the directory/filter/map layouts Days 13-19 will need.
8. **The spacing scale uses Tailwind-style step numbers (`--space-N` = `N * 0.25rem`), not a fresh naming scheme.** This was chosen because it let every exact value the Day 1 landing page already used (0.75rem, 1.25rem, 1.75rem, 2.5rem, 3.5rem, 4rem, 5rem, 7rem) map onto a named step without changing any rendered output, and it's a convention many contributors (human or AI) will already recognise, lowering the chance of a later Day introducing an unrelated spacing system by accident.

## How later Days should extend this

- **Adding a nav item:** once its target page exists, add an `<li>` to `SiteHeader.tsx`'s list. At that point, also switch the component to compute `aria-current` from `usePathname()` (`"use client"`) instead of the current hardcoded value - see the comment left in that file.
- **Adding a breakpoint-dependent layout** (e.g. the directory's card grid, the map's split view): reuse `--bp-sm`/`--bp-md`/`--bp-lg` from the comment at the top of `globals.css` as literal values in new `@media` rules, rather than picking a new breakpoint value.
- **Adding spacing, type-scale or radius values:** extend the existing `--space-N` / `--text-*` / `--radius-*` token lists in `:root` rather than hardcoding a new magic number inline, so the full set stays discoverable in one place.
- **Footer contact/sitemap links:** `SiteFooter.tsx` is intentionally minimal (name, tagline, year) because Days 13-26 haven't built the pages a fuller footer would link to yet. Extend it once there's somewhere real for those links to go.

## Open items carried forward

- No directory, detail, map, admin or enquiry pages exist yet - Days 13-26 build those, at which point `SiteHeader`'s nav should grow beyond "Home only" per decision 2 above.
- No dark-mode / `prefers-color-scheme` handling - `globals.css` currently declares `color-scheme: light` outright. Not requested for the MVP; noted here in case it becomes a later requirement.
- `--bp-md` and `--bp-lg` are declared but not yet used by any rule - they exist now so the scale is established before the layouts that need them (filters, map split-view) are built.
