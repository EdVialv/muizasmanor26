# Day 10 — idempotent importer and representative-sample load

This is the Day 10 deliverable from `TODO.md`: an idempotent, batched, resumable importer, run against `data/sample/day4-representative-records.csv` (the Day 4 representative sample). It adds a staging schema (`supabase/migrations/20261024173045_import_staging.sql`) and an importer CLI (`scripts/import/`), both documented in detail in the migration's own header comment and this file.

## What this delivers

- `supabase/migrations/20261024173045_import_staging.sql`: an `import_row_status` enum matching `docs/DAY6_NORMALIZATION_RULES.md` section 5's four-state machine exactly, a `staging_heritage_objects` table, and a `promote_staging_row(uuid)` function that inserts a ready staging row into `heritage_objects` plus its historical-owner-family and cadastre-reference children, resolving parent linkage through the staging table itself.
- `scripts/import/`: a TypeScript CLI (`npm run import -- ...`) that loads the uncommitted `.env.local`, parses a CSV shaped like the Day 4 sample, resolves/validates each row against `heritage_objects`' own `NOT NULL` contract, upserts into staging (batched, idempotent, skip-if-unchanged), and optionally promotes whatever reaches `ready_for_import`.
- Unit tests (`scripts/import/parseSample.test.ts`) for the pure parsing/validation logic, and a full local-Postgres integration run exercising staging, idempotent re-runs, the "changed after import" guard, and promotion with real parent/child linkage and real family data (see "Verification performed" below).

## Decisions made while writing this (flagged for Codex review)

1. **This sample has no natural stable source identifier**, unlike the real blog dataset's `Bloga ieraksta Nr.` (`docs/DAY6_NORMALIZATION_RULES.md` section 2). Its `slug` column is already unique and stable within the file, so the importer uses `external_source_id = slug` with `source_system = <the --source-system flag value>` (this session ran it as `day4_representative_sample`). This reuses the existing `(source_system, external_source_id)` idempotency pattern rather than inventing a new one.
2. **This importer never assigns `archived_out_of_scope` and never runs a scope/keyword classification.** `docs/DAY6_NORMALIZATION_RULES.md` section 1's manor-vs-everything-else scope decision applies to the raw blog dataset's free text; every row in this hand-curated sample is already a type a human researcher selected as in-scope (confirmed valid `object_type` values throughout). A real run against the raw dataset (Day 11's dry run) is where that classification actually needs to happen, and should design it against real raw rows rather than against this already-curated shape.
3. **`summary_research_en` is never mapped to `summary_lv`, under any circumstance.** It is the researcher's internal English note, not publishable Latvian text, and the Day 4 Codex review already concluded this sample is "a research artifact, not import-ready or publishable content" (see `PROGRESS.md`'s 2026-10-08 Codex entry). Because `summary_lv` is a required field and this CSV format has no column for it at all, **every row in this sample can only ever reach `needs_review`, never `ready_for_import`, through the importer alone** - confirmed in the verification run below. This is the contract working as intended, not a bug: `docs/DAY6_NORMALIZATION_RULES.md` section 5 is explicit that a candidate "must not silently create a canonical object that violates the contract."
4. **`source_accessed_at` is mapped directly to `last_verified_at`.** Both describe the one check this sample's research actually performed against its cited source, so treating them as the same fact is a reasonable reading of intent, unlike `summary_lv` which would require generating new Latvian prose.
5. **`promote_staging_row()` never sets `heritage_objects.status` to anything but its table default (`draft`).** Publishing is an editorial act (`TODO.md` Day 22+), never an automatic side effect of import.
6. **A row already `imported` is not silently re-staged or re-promoted when its source value changes.** Once promoted, `heritage_objects` is the live source of truth, not the staging row. A changed source row updates `raw_payload`/`raw_payload_hash` for traceability and appends a note to `status_reason`, but leaves `status = 'imported'` and the resolved fields untouched - verified below. Re-promoting a changed row is a deliberate future action (e.g. a `--force`-driven re-sync into `heritage_objects` itself), not implemented here, since it is not needed by anything this day's scope requires.
7. **`cadastre_references` is never parsed from this CSV**, even though the staging table, the jsonb shape and `promote_staging_row()` all support it. Every row's `cadastre_references` column is empty in this sample, and Day 5's mapping found "zero source signal" for cadastral data in the real blog dataset too - so there is no real data anywhere yet to design a parser against. If the column ever holds a value, the importer flags it as an unresolved issue (forcing `needs_review`) instead of silently discarding it.
8. **Historical-owner-family free text is stored as one `family_name` string per entry, not decomposed into separate alternate-spelling/year fields**, and a `"(none confirmed ...)"` sentinel (which contains its own semicolon) is recognised and treated as zero families rather than naively split - both covered by unit tests. Extracting structured years/alternate names from this free text would require real text analysis, not a format decision, and is left for whoever eventually builds that editorial tooling.
9. **Batching and resumability are achieved through a per-batch transaction plus a content hash (`raw_payload_hash`)**, not a separate job-tracking table. A crash mid-run only loses its current (uncommitted) batch; a re-run skips every row whose source content has not changed, and only re-evaluates the ones that did (or everything, with `--force`). This matches `docs/ARCHITECTURE.md`'s "idempotent, batched, resumable" requirement without inventing machinery nothing else in this project asks for.

## Verification performed

Same methodology as every prior migration day - this session holds no real Supabase credentials, so this was run against a disposable local Postgres 16 + PostGIS + pg_trgm instance with `anon`/`authenticated`/`service_role` mirrored locally (`service_role` given `LOGIN` and a throwaway local password purely so the Node importer could connect to it; neither exists outside this disposable database):

- Applied the Day 8, Day 9 and this Day 10 migration in sequence - all applied cleanly.
- `select promote_staging_row(...)` exercised directly in `psql` against a synthetic parent/child pair plus a synthetic cadastre reference before the TypeScript layer was even written: a child staging row correctly raised `SQLSTATE MM001` when attempted before its parent was promoted; promoting the parent then the child succeeded, produced the correct `parent_object_id`, and inserted the expected family and cadastre-reference rows; re-promoting the already-`imported` parent correctly refused (`promote_staging_row` only accepts `ready_for_import` rows), proving the guard against double-promotion.
- `npm run import -- --file data/sample/day4-representative-records.csv --source-system day4_representative_sample --promote` run against the real sample: **all 25 rows staged as `needs_review`, zero `ready_for_import`, zero promoted** - every row is missing `summary_lv` (decision 3), several also missing `latitude`/`longitude`, and the `Mežotnes pilskalns` row additionally missing `municipality`, exactly matching that row's own notes column ("Coordinates and municipality could not be confirmed from source").
- Re-ran the same command: all 25 rows reported `skipped_unchanged`, proving the hash-based resume path works and the run is fully idempotent (`staging_heritage_objects` row count stayed at 25, not 50).
- Simulated an editor completing `summary_lv` directly on the Rundāle trio's staging rows (parent `rundales-pils` plus children `rundales-pils-parks` and `rundales-pils-zirgu-stalli`), set to `ready_for_import`, then re-ran the importer: it did **not** clobber the manual edit (content hash unchanged → skipped), and the `--promote` pass correctly promoted all three in one run - the parent first, then both children once the parent was visible, confirming the retry loop works on real data, not only the synthetic fixture. Verified in `heritage_objects` that both children's `parent_object_id` correctly points at the parent's generated id, all three default to `status = 'draft'`, and `object_historical_owner_families` has the right family rows for each (`von Biron`, `Zubov`, `Shuvalov` for the parent; the correct subset for each child, matching each row's own semicolon-separated list).
- Re-ran again after promotion: zero duplicates (`heritage_objects` stayed at exactly 3 rows for this source), confirming promotion is also stable under re-runs.
- Modified the already-imported `rundales-pils` row's source `notes` text and re-ran without `--force`: this caught one real bug (an SQL parameter referenced in the parameter array but never used in the query text, which Postgres rejected with "could not determine data type of parameter $2") - fixed in `scripts/import/db.ts`, then re-verified: the staging row's `status` stayed `imported`, `status_reason` gained the "source row changed after import; re-import not automatic" note, and the canonical `heritage_objects` row was untouched, exactly matching decision 6.
- Dropped the scratch database and the three mirrored roles afterward; nothing from this test run persists anywhere.
- `npm run format:check`, `lint`, `typecheck`, `test` (17 tests, including 10 new ones in `scripts/import/parseSample.test.ts`) and `build` all passed. `build` surfaced an unrelated, pre-existing Next.js security-advisory gate (Next.js 16.0.0-16.4.0 has a disclosed RCE in its Image Optimization API, among other advisories; `npm audit` shows the same finding) - it stops the build once with an upgrade recommendation and continues on retry. This was not introduced by this change and is not fixed here; it is a separate, repo-wide dependency-upgrade decision for the owner, not part of Day 10's scope.

## Running this against the real project

Once Day 8, Day 9 and this Day 10 migration are applied to `muizasmanor26-dev`, set `SUPABASE_DB_URL` in `.env.local` (already reserved since Day 7) to that project's **direct** connection string - the importer needs a role that can write past RLS, i.e. the same connection Supabase's own migrations use, not the `anon`/`authenticated` Data API. Then:

```bash
npm run import -- --file data/sample/day4-representative-records.csv --source-system day4_representative_sample --promote
```

Expect the same result documented above: 25 rows staged, all `needs_review`. An editor must fill in each row's `summary_lv` (and, for several rows, coordinates/municipality) directly in `staging_heritage_objects` and then set that row's `status` to `ready_for_import`. The database constraint rejects that status while any required field is still missing. A repeat run with `--promote` then picks the row up.
