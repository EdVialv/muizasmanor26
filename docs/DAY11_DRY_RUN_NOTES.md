# Day 11 — real raw-dataset dry run

This is the Day 11 deliverable from `TODO.md`: "Run an import dry run, inspect failures, fix transformations and document resume/rollback procedures." Per this session's explicit instructions, Day 11 begins as a **non-destructive dry run and failure report only** - it does not rerun any migration and does not bulk-promote any raw record. `scripts/import/day11DryRun.ts` never imports `db.ts`, never opens a database connection, and never touches `supabase/migrations/`; it only reads the real workbook and writes a report file. This was verified by grep, not just by inspection (see "Verification performed").

## What this delivers

## Decisions made while writing this (flagged for Codex review)

1. **The real workbook is never committed to this repository.** It is a large (~10MB), owner-provided binary export, not source code. `.gitignore` reserves `/data/raw/` as a conventional local path for it, but `--file` accepts any path, so no specific location is required. Only this run's derived report is committed.
2. **This session's uploaded workbook has a different SHA-256 and byte size than the one Codex recorded in `docs/DAY5_COLUMN_MAPPING.md`** (`0721c7a8342cf3f118b3cd464d784e67ed6722f940eeb2f47ac077415ceb460e`, 10,541,965 bytes here vs. `49e8ca0d5c61e22f91bcf5a2bdfb4a75a73704ae23b3545a8c26948f7b64f199`, 9,799,262 bytes there) - almost certainly a different save/export instance of the same source data rather than different data, since every structural figure this dry run independently computed matches Day 5's findings exactly: 16,800 image rows, 3,716 unique posts, 505 posts with no resolved coordinates, 26 with no resolved address, 17 outside the approximate Latvia bounding box, and the same 2/4/12 within-post variant counts for address/coordinates/body text. Still, this should be confirmed with the dataset owner rather than assumed, which is why both fingerprints are recorded here rather than silently treated as interchangeable.
3. **Scope triage (section 1) by itself only ever proposes, never finalises - but decision 10 below extends it into a real, confirmed two-state decision for this dry run.** The raw title-keyword triage (`scopeTriage`) remains "a triage aid only, never the final classification by itself," exactly as section 1 originally requires, and is still recorded for audit. What changed: every post now additionally gets a `scopeDecision` ("in_scope" | "archived_out_of_scope") and a `scopeDecisionBasis` recording exactly which signal produced it, so `proposedStatusPendingConfirmation` is `false` throughout this report rather than permanently `true`. See decision 10 for the methodology and why `archived_out_of_scope` is a real decision rather than a placeholder.
4. **`object_type` is never auto-assigned, even for `in_scope_candidate` posts.** A manor-keyword match does not by itself tell you `manor_estate` vs. `manor_house`, and a castle-keyword match does not tell you `palace_or_castle` vs. `ruin_or_historical_site`. This is a per-post human judgment call, so every post - including clearly in-scope ones - keeps `object_type` in its `issues` list permanently, pending that review.
5. **`municipality` is never derived from the free-text `Adrese` column.** `docs/DAY6_NORMALIZATION_RULES.md` describes this as "embeddable but needs parsing, not a 1:1 copy" without specifying an extraction algorithm, and warns against deriving it blindly from a `location_hint`. Rather than invent a parsing rule the project hasn't agreed on, this dry run leaves `municipality` unmapped and flags it as missing on every post.
6. **The consequence of decisions 4-5, plus `last_verified_at` and `summary_lv` already having no source signal at all (confirmed in `docs/DAY5_COLUMN_MAPPING.md`'s "no source column" list): no post in this entire ~3,716-post dataset can ever reach `ready_for_import` through automation alone.** This is the same structural finding `docs/DAY10_IMPORTER_NOTES.md` decision 3 already proved on the 25-row hand-curated sample, now independently confirmed at full real-dataset scale. It is the contract working as intended, not a bug - see the verification numbers below.
7. **Duplicate-candidate matching is normalised-name equality, or near-identical coordinates corroborated by at least partial name evidence - never coordinates alone (see decision 11.3 for a Day 11 Codex review correction to this rule).** Exact name matches still produce expected false positives for common/generic manor names - several of the 165 duplicate candidates come from posts that simply share a common name (e.g. multiple distinct posts named some variant of "Jauna muiža," literally "New Manor") rather than describing the same physical place. This is inherent to the documented rule, not a defect in this implementation; a human reviewer should weight coordinate-corroborated pairs above bare name matches for generic names.
8. **The 17 posts outside the approximate Latvia bounding box are flagged generically, not split into "foreign" vs. "malformed."** Day 5/Codex's prior manual pass already did that split for their export (15 genuinely foreign, 2 malformed Latvian coordinates); reproducing that specific judgment call from scratch here would risk exactly the "guess instead of verify" outcome this session was told to avoid, so this dry run reports the bounding-box violation and leaves the foreign/malformed distinction to manual re-check.
9. **`exceljs`, not the `xlsx` (SheetJS) npm package, parses the workbook.** The `xlsx` package's latest npm release (`0.18.5`) carries two long-standing, npm-unpatchable high-severity advisories (prototype pollution, ReDoS) - SheetJS only ships patched builds through its own CDN, not npm. `exceljs` is dev-only here, keeps `npm audit --omit=dev` at zero vulnerabilities, and its own new transitive advisory (an outdated `uuid`, dev-only) never reaches production.
10. **The Day 11 scope-confirmation pass: a real, confirmed `in_scope`/`archived_out_of_scope` decision for every post, based on the dataset's own text - title and body - never guessed or looked up externally.** Requested explicitly ("Manual scope confirmation pass... record real in/out-of-scope decisions, instead of leaving them as unconfirmed proposals") rather than left as the three-bucket title-only proposal from decision 3/section 1. The rule, applied per post:

- If the title alone already names a manor/palace/castle/hillfort (`scopeTriage === "in_scope_candidate"`), the decision is `in_scope` with `scopeDecisionBasis: "title_keyword"` - this is just the existing title rule, carried through unchanged.
- Otherwise, the post's own collapsed body text (the longest non-placeholder variant across its image rows, section 3's existing rule - no new text source) is scanned for an explicit manor-complex-**membership** phrase: `findManorAffiliationPhrase()` in `rawDatasetTransform.ts`, five tight regexes (`muižas komplekss/ansamblis/teritorija/parks/klēts/kūts/stallis/dzirnavas/kapela/skola/pārvaldnieks/saimniecība`, `piederēja muižai`, `bijušās muižas <noun>`, and the two-word `muižas pils`/`pils muižas`). A match produces `in_scope` with `scopeDecisionBasis: "body_text_affiliation_phrase"` and records the matched phrase in `bodyTextAffiliationPhraseMatched` (and in the post's own `issues` list) for a full audit trail.
- If neither signal fires, the decision is `archived_out_of_scope` with `scopeDecisionBasis: "no_signal_found"`.
- **Deliberately tighter than a bare substring match.** A naive `/muiž\w*/` or `/pils\w*/` test would also fire on text that only mentions a manor's _proximity_ ("south of the manor", "near the manor park") without saying the post's own subject belongs to it - that would just reproduce the title scan's false-positive problem one level down. The phrase list requires an actual membership/possession construction, not a bare mention.
- **A real regex bug was caught and fixed during verification, and is recorded here as a cautionary note for anyone extending these patterns.** The first draft used `\w*` to extend a Latvian word stem (e.g. `bijuš\w*` intending to match `bijušās`). `\w` in JavaScript - even with the `u` flag - only matches ASCII word characters, so it cannot cross a diacritic (ā/č/ē/ģ/ī/ķ/ļ/ņ/š/ū/ž) that falls _after_ the pattern's literal ASCII prefix; `bijuš\w*` against `bijušās` matches only `bijuš` and then fails to continue into `ās`, silently breaking the whole phrase match. All five patterns now use `[\p{L}]*` instead, which matches any Unicode letter. A second, distinct bug of the same family: the `\bpils\w*\s+muiž\w*` pattern used a bare `\b` word-boundary at the _start_ of "pils" but then let `\w*`/`[\p{L}]*` consume as many trailing letters as it liked - so it matched "Pilskalnes muižnieks" by treating the toponym "Pilskalnes" as if it were "pils" + "kalnes", exactly the place-name false-positive `scanKeywordGroups`' word-boundary-safe exact-word check was already built to avoid for "pils" in titles (Ventspils/Jēkabpils/Mālpils). Fixed with lookaround (`(?<![\p{L}])pils(?![\p{L}])`) so "pils" must be a complete word, not just a prefix. Both fixes are covered by regression tests in `rawDatasetTransform.test.ts`.
- **What this pass cannot catch:** any affiliation that isn't stated in the post's own title or body text at all - e.g. a photo caption that shows a building is on manor grounds, or outside knowledge of local history. Those posts land in `archived_out_of_scope` by default, not because they are necessarily out of scope, but because this dataset gives no textual signal either way. This is the honest limit of a text-signal-based pass, not a guess dressed up as certainty.
- **`archived_out_of_scope` is a real decision here, not a placeholder - but it is still reversible.** Section 1 itself frames scope as "a product decision, not a permanent one": an archived post keeps its stable `external_source_id` and all its data, it is simply not staged for import. Nothing in this dry run deletes anything or writes the decision anywhere outside this report.
- Changed `duplicateCandidates.ts`'s `buildCandidateQueues` to filter on the new `scopeDecision === "in_scope"` instead of the old `scopeTriage === "in_scope_candidate"`, so the duplicate/relationship review queues now include the posts the body-text pass reclassified into scope (see updated counts below).

11. **Four corrections made in response to a Codex review of the Day 11 work above, on the same branch.** Each is a genuine code-correctness fix, not a stylistic change, and each is covered by new regression tests. For every one, this section also records what re-running the dry run against the _same_ real workbook actually showed - which, honestly, is "no change to the headline numbers" for three of the four, because this specific dataset doesn't happen to exercise the edge case the bug affected. That is a property of this dataset, not evidence the bugs were harmless in general; the fixes stand regardless, since a different export or a future batch of this same dataset could easily hit them.

    1. **Global slug uniqueness (`resolveSlugCollisions` in `rawDatasetTransform.ts`).** The previous implementation only checked a collision-derived slug (base + location hint, or base + external id) against other collision-derived slugs assigned so far in the same pass - never against an unrelated record's own unique base slug. Worked example: "Foo" with location hint "Bar" derives "foo-bar"; a separate, unrelated record titled "Foo Bar" has "foo-bar" as its own unique base slug; nothing stopped both records from ending up with the identical final slug "foo-bar". Fixed by reserving every unique base slug globally, up front, before resolving any collision group, plus a last-resort incrementing-counter fallback for the (expected-impossible-in-practice) case where even that isn't enough. Four new tests, including the exact worked example above and its order-independence. **On the real workbook:** re-derived all 3,716 posts' slugs from both the old and the fixed algorithm directly against the real title data and found zero actual duplicate final slugs under _either_ version - this dataset's real titles never happened to produce the specific base-slug/derived-slug collision this bug required. `slugCollisionGroups` in the report is unchanged at 72 (that count was never wrong; it's a legitimate collision-group count, not the bug).
    2. **Unbalanced parentheses (`extractPrimaryName` in `rawDatasetTransform.ts`).** `extractPrimaryName("Some title (unbalanced")` returned `ambiguousParentheses: false` - wrong, and the project's own existing test asserted that wrong value as correct despite being titled "flags an unbalanced parenthetical group as ambiguous". The root cause: `firstBalancedParenGroup` returned the same `null` for "no `(` at all" and "a `(` that's opened but never closed", so `extractPrimaryName` couldn't tell them apart. Fixed by replacing it with `firstParenGroup`, which returns a three-way `{kind: "none" | "unbalanced" | "found", ...}` result; only `"unbalanced"` (and the pre-existing leading-group/empty-prefix case) now sets `ambiguousParentheses: true`. The existing test was corrected to expect `true`, and a new test directly contrasts an ordinary no-parentheses title against an unbalanced one. **Also clarifying the "missing parentheses" case, as asked:** section 2's rule sentence reads as one clause covering "missing, unbalanced or ambiguous" together, but section 2's own worked-example table immediately treats a title with no parenthetical group at all as a perfectly ordinary, unflagged example - and Day 5 found the majority of titles don't use the "(alternates) location" convention at all. Flagging every one of those for manual review would bury the two cases that actually need it (malformed syntax) in noise, so this implementation keeps "missing" as the ordinary, non-ambiguous case and only flags genuine syntax problems. This is a judgment call on an ambiguous sentence, documented here explicitly so Codex/the owner can override it if the stricter reading was actually intended. **On the real workbook:** the regenerated report's `issueFrequency` shows zero occurrences of the ambiguous-parentheses issue message - no real title in this dataset has an unbalanced or leading parenthetical group, so this fix also did not change any real output, though it is now correct for any dataset that does have one.
    3. **Duplicate vs. relationship classification (`buildCandidateQueues` in `duplicateCandidates.ts`).** docs/DAY6_NORMALIZATION_RULES.md section 4 is explicit that "proximity alone is not evidence of duplication," but the previous implementation treated any pair of in-scope posts with coordinates under 20m apart as a duplicate candidate unconditionally, with no name check of any kind. Fixed by adding `namesShareEvidence()` (exact match, substring containment, or a shared 4+ character word between the two normalized primary names) and requiring it alongside near-identical coordinates before a pair is promoted to the duplicate queue; near-identical pairs that fail the name check now fall through to the relationship queue instead, same as any other pair within 500m. Four new/updated tests, including an explicit positive case (near-identical coordinates + overlapping names -> duplicate) and negative case (near-identical coordinates + unrelated names -> relationship, not duplicate). **On the real workbook:** 165 duplicate candidates (164 `name_match`, 1 `near_identical_coordinates`) and 92 relationship candidates - identical totals to before this fix. The dataset's one actual near-identical-coordinates pair (posts 2873/3564, 2.3m apart) already shares the significant word "nabes" between its two titles, so it was already correctly a duplicate candidate either way; this dataset simply never contained a near-identical-but-unrelated-names pair for the fix to reclassify. The duplicate candidates' `detail` text for coordinate-based matches now names the shared evidence explicitly, which is a real (if small) output change.
    4. **Excel hyperlink extraction (`cellText`/new `cellHyperlinkOrText` in `day11DryRun.ts`).** An ExcelJS hyperlink cell's value is `{ text, hyperlink }` - both a displayed label and the actual link target - but `cellText()` checked for a `.text` property before a `.hyperlink` property, so for every hyperlink-shaped cell it silently returned the displayed text and never reached the hyperlink branch at all. This matters specifically for the three URL columns (blog-post URL, Google Drive hyperlink, original image URL), where the link target is the actual data, not whatever label happens to be displayed. Fixed by adding `cellHyperlinkOrText()` (prefers the hyperlink target, falls back to `cellText()` for a plain cell) and using it only for those three columns; every other column (title, address, coordinates, caption, body text) still correctly uses `cellText()`, since a hyperlinked title cell's own text, not some unrelated target, is what a title column should hold. New tests cover all four cases Codex asked for directly (blog-post URL, Drive URL, original image URL, and an ordinary plain-text URL cell with no hyperlink formatting), both as isolated cell-shape unit tests and as an end-to-end test that builds a real temporary `.xlsx` workbook with ExcelJS and reads it back through `readWorkbookRows`. Also added a new `imageIdentitySourceCounts` report statistic (`drive_file_id` / `original_url` / `content_hash` tallies across every image), per Codex's request, specifically so this exact kind of silent extraction failure is visible in every future report rather than only discoverable by code review. **On the real workbook:** inspected the actual cell shapes directly and found that for every one of the 16,800 image rows, across all three URL columns, the hyperlink cell's `.text` and `.hyperlink` values are byte-for-byte identical (this particular export's "friendly label" is simply the full URL again, not a shortened one) - so the bug, while real, never actually produced a wrong value in this specific workbook. `imageIdentitySourceCounts` confirms `drive_file_id: 16800, original_url: 0, content_hash: 0` under both the old and new extraction logic (verified directly, not just inferred). The fix remains necessary: a different export, or a future batch from the same source blog, could easily have a cell where the display label and the target genuinely differ.

## Running this against the real project

No database connection is needed for the dry run itself:

```bash
npm run day11:dry-run -- --file /path/to/muizasdb_pic.xlsx --out-dir docs/day11-dry-run-output
```

This overwrites the two report files in `--out-dir` and prints a short summary to stdout. Re-running is always safe (see "Resume" below). Review `day11-dry-run-report.md` for the full breakdown, then work through the "Open items" below - in particular the scope-confirmation and `object_type`/`municipality` manual passes - before anything from this dataset is staged into `staging_heritage_objects` by a future importer run.

## Resume and rollback procedures

- **Resume:** the dry run is a pure function of the workbook's bytes - it reads the file, computes everything in memory, and writes the report. There is no partial state to resume: if it is interrupted, simply re-run the same command. A second run overwrites the report deterministically (verified by the collision-resolution order-independence test); it never appends, accumulates, or depends on a previous run having completed.
- **Rollback:** this dry run writes nothing to any database, local or real, so there is nothing from this day's work to roll back. For whoever later builds the actual staging load on top of this report (Day 12+, reusing `scripts/import/db.ts`'s `upsertBatch`/`promoteReadyRows`): follow the same resumable pattern `docs/DAY10_IMPORTER_NOTES.md` already established - a content-hash skip makes re-running safe, and `promote_staging_row()`'s parent-retry loop handles ordering. If a staged batch needs undoing before promotion, delete the affected `staging_heritage_objects` rows by `(source_system, external_source_id)`. Once a row reaches `imported`, `docs/DAY10_IMPORTER_NOTES.md` decision 6 already establishes that `heritage_objects` - not the staging row - is the source of truth; the correct rollback at that point is deleting the specific `heritage_objects` row(s) created (children before their parent, to respect the hierarchy foreign key), not editing the staging row.
